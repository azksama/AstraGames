# Audit UI/UX Astra — 5 octobre 2026

## Périmètre et niveau de preuve

Ce rapport consolide la **revue statique des 39 fichiers Kotlin de production sous `ui/` (8 405 lignes)**, répartie entre les volets interface, sécurité/localisation et relecture complémentaire, ainsi que les preuves Android de cette session. Il ne signifie pas qu’un seul intervenant a exécuté chaque écran. L’inventaire complet figure plus bas ; les appels importants ont été recoupés avec contrôleurs, stockage et flux d’état.

La grille de lecture est celle d’**Impeccable, audit natif Android** : accessibilité, performances, apparence, conventions Android et adaptation. La [revue Emil](AUDIT_UI_EMIL_2026-10-05.md), demandée explicitement, complète ce travail sur le feedback, le focus, les sémantiques et la lisibilité. La direction existante décrite dans `DESIGN.md` est conservée : Compose/Material 3, palette sombre personnalisable, jaquettes prioritaires, navigation compacte et rail sur fenêtres larges. Il s’agit d’améliorer les parcours existants, pas de remplacer leur identité visuelle.

**La confirmation Android après les correctifs Emil a réussi 61 tests sur 61 en portrait à 100 %, puis deux passes de 32 tests UI sur 32 en paysage et portrait à 150 %, sur l’émulateur SDK API 36.1.** La suite complète inclut les parcours UI et des vérifications natives ML Kit, Android Keystore et SAF. Les captures inspectées sont listées plus bas. Ni une session TalkBack, ni une mesure de fluidité, ni un essai sur téléphone physique ou jeu réel ne sont revendiqués. La présence de `rememberSaveable`, de sémantiques ou d’insets n’est pas une preuve d’exécution correcte sur tous les appareils.

Validation hôte finale après les derniers ajustements UI : **200 tests JVM dans 39 suites**, sans échec, erreur ni test ignoré ; builds debug/release R8, APK de tests Android et Baseline Profile réussis ; lint sans erreur, avec 45 avertissements. Journal : `build/audit-verification-delivery-final-1.10.0.log`, `BUILD SUCCESSFUL in 58s`, 200 tâches dont 33 exécutées et 167 à jour. Les journaux précédents restent des traces intermédiaires, pas la preuve du dernier état des sources.

Les résultats JUnit relus sont `OK (61 tests)` dans `build/emulator-validation/instrumentation-confirmed-portrait.log` (198,499 s), et `OK (32 tests)` dans `instrumentation-confirmed-landscape-large-text.log` (132,522 s) et `instrumentation-confirmed-portrait-large-text.log` (124,801 s). Les 32 scénarios UI sont réexécutés sous deux autres configurations, pas ajoutés au nombre de tests uniques. Les deux matrices à 150 % précèdent la dernière correction des libellés anglais ; la disposition française testée reste inchangée. La suite complète de 61 tests et le lancement R8 ont été réexécutés après cette correction. Le [rapport Android](ANDROID_VALIDATION_2026-10-05.md) centralise les configurations, captures et l'essai de lancement réussi d'une copie de test de l'APK optimisé R8. Les builds restent centralisés dans [le rapport global](AUDIT_2026-10-05.md).

## Conformité native et appréciation du code

La structure observée correspond à une application Android native : composants Material, listes Compose virtualisées, clavier et barres système pris en compte, destinations adaptées à la largeur. Les WebViews servent aux parcours web explicites de recherche/connexion ; elles ne remplacent pas l’interface principale. La navigation en pilule et les en-têtes défilants sont des choix existants documentés, conservés dans cette passe.

Les notes suivantes restent **heuristiques**, issues du code après correction et complétées par les observations sur émulateur. Elles ne constituent pas une certification de qualité sur tous les appareils ; les limites de chaque dimension restent explicites.

## Problèmes corrigés et parcours concernés

Les priorités ci-dessous décrivent l’impact avant correction. Les 12 constats initiaux sont regroupés par cause : 6 P1, 5 P2, 1 P3. Cinq constats complémentaires P2 issus de la revue Emil et des captures figurent ensuite. Ils ne constituent pas un décompte exhaustif des défauts possibles de l’application.

| ID / priorité | Déclencheur et impact | Correction visible dans le code |

| UI-01 / P1 | Quitter ou recréer l’éditeur pouvait perdre un brouillon, même si son contenu était encore utile. | `SaveScreens` conserve brouillons, onglet, recherche, filtre et confirmation via `rememberSaveable`/`mapSaver`. Le retour et Annuler demandent confirmation si des modifications subsistent, y compris après un échec de rechargement. |
| UI-02 / P1 | Recréer l’éditeur après modification externe du slot pouvait associer un ancien brouillon à une nouvelle révision. | UI-03 / P1 | Un titre, tag, dossier, texte de sauvegarde ou autre contenu utilisateur identique à une clé de traduction pouvait être modifié à l’affichage. | Séparation explicite entre libellés localisés et données affichées par `MaterialText`. | UI-04 / P1 | Les WebViews de métadonnées permettaient une navigation vers des schémas ou ressources hors de leur parcours réseau. | Politique partagée `WebViewSecurity` : HTTPS, sans userinfo ni port arbitraire ; accès fichiers/contenu et mixed content désactivés ; domaine du fournisseur contraint pour la connexion ; contrôle de navigation et interception des requêtes principales, y compris POST. |
| UI-05 / P1 | Le verrouillage initial pouvait attendre la fin de travaux d’initialisation au lieu de prendre effet dès la lecture des paramètres. | `AstraViewModel` applique l’état verrouillé avant récupération de scans, configuration des workers et scan automatique. | UI-06 / P1 | Le test d’un profil de lancement pouvait contourner le contrôle d’une traduction incomplète. | `translationReadyToLaunch` est partagé par lancement normal et test de profil. Une traduction active, un journal incohérent ou une écriture interrompue empêche le lancement. |

| UI-09 / P2 | La sélection de tags ne décrivait pas toujours son rôle/état ; une sélection supprimée pouvait rester active. | UI-10 / P2 | Aucun parcours guidé ne permettait de remettre les textes à une IA puis de charger le résultat sans éditer les fichiers du jeu à la main. | Onglets « Sur cet appareil » / « Fichier pour IA », export SAF, consignes incluses, import avec confirmation puis validation, états de progression et erreurs. ### Sauvegardes : rendre la décision compréhensible

Le mode simple propose les champs reconnus ; le mode avancé donne les chemins complets, types, recherche et favoris. L’utilisateur voit désormais une erreur de valeur avant l’écriture. Enregistrer reste désactivé si le brouillon est vide, invalide ou qu’une opération est en cours. Le rappel de fermer le jeu et la limite Ren’Py figurent dans l’éditeur. Le bouton Retour n’efface pas silencieusement les changements.

Le formulaire est isolé dans `SaveScreens.kt` et les listes de mods dans `ModsScreen.kt`, au lieu de concentrer ces parcours dans `GameToolsScreens.kt`. La restauration d’une copie indique que le slot courant sera remplacé avec conservation d’une copie préalable. La protection exacte des écritures, types et formats est décrite dans [l’audit sauvegardes](AUDIT_SAVE_2026-10-05.md).

### Traduction : distinguer les deux modes et leurs garanties

Le mode local conserve les options de langues et Wi-Fi. Le mode manuel explique que l’utilisateur choisit lui-même une IA et doit modifier uniquement `translation`, en conservant IDs, sources et marqueurs. Le choix du fichier ne déclenche pas immédiatement son application : une confirmation rappelle de fermer le jeu, puis le backend vérifie l’ensemble de l’échange avant écriture.

L’import et l’export signalent les erreurs sans faire passer un texte conservé pour une traduction réussie. Une destination contenant déjà des données est refusée. Une traduction déjà installée donne accès à la restauration avant une nouvelle opération. Le périmètre MV/MZ et les exclusions sont affichés ; le mode manuel ne promet pas de traiter les scripts, images ou formats libres de plugins. L’interface précise aussi que les noms utilisés dans les conditions du jeu sont conservés : traduire ces noms casserait les comparaisons avec les noms déjà enregistrés dans les sauvegardes existantes. Voir [le mode d’emploi](MANUAL_TRANSLATION.md) et [l’audit traduction](AUDIT_TRANSLATION_2026-10-05.md).

### Localisation : préserver le contenu utilisateur

Les corrections concernent les cartes et fiches de jeux, sources, collections, tags, métadonnées importées, chemins et champs d’éditeur. Elles n’ajoutent pas une traduction automatique des descriptions ou noms de jeux. Le catalogue reçoit les nouveaux textes de parcours dans les sept langues prises en charge. Le relevé exact des clés et tests associés se trouve dans [la revue UI/localisation](AUDIT_UI_LOCALIZATION_2026-10-05.md).

## Refactorisation et limites structurelles

La séparation `GameToolsScreens` / `SaveScreens` / `ModsScreen` réduit le mélange de parcours et permet de relire l’éditeur sans le catalogue de mods. `WebViewSecurity` remplace plusieurs configurations divergentes. Les primitives de localisation portent explicitement la différence entre interface et contenu, au lieu de tenter de la déduire de la valeur d’une chaîne.

`AstraViewModel` reste volumineux (**environ 1 157 lignes**) et orchestre de nombreuses fonctionnalités. `Localization` atteint **820 lignes**, `MetadataScreens` **661**, `GameDetailScreens` **510** et `LibraryScreens` **436**. Ces volumes sont constatés, pas masqués par le mot « refactorisation ». Une extraction progressive de contrôleurs de métadonnées/lancement et de composants de fiches serait raisonnable lors de prochains changements ; cette session ne revendique pas une réécriture intégrale de ces modules.

La revue n’établit pas une absence totale de code mort, une couverture de branches à 100 % ou une optimisation mesurée. Les anciens imports inutilisés et certains paramètres hérités peuvent encore être signalés par lint. Les textes historiques sans entrée de catalogue peuvent rester français. Le catalogue applicatif n’a pas été entièrement migré vers les ressources Android.

## Pratiques conservées

- Les titres/jaquettes guident les parcours de bibliothèque et les noms utilisateur restent intacts.
- Les composants Material, les unités `sp`, les rôles de couleur et les tailles minimales de contrôle fournissent un socle natif cohérent.
- Les résultats importants ont des clés stables dans les listes/grilles ; les calculs de filtrage et d’index sont séparés du rendu.
- Les opérations potentiellement longues exposent progression/erreur, et les écritures de sauvegardes disposent de contrôles de révision.
- Les modes téléphone/paysage utilisent des listes défilantes et largeurs bornées ; les formulaires importants intègrent les insets IME.
- Les tests JVM existants de collections, recherche, récents et palette sont conservés. Leurs résultats actuels doivent être lus dans le rapport global, pas déduits de leur seule présence.

## Validation native et limites restantes

Les corrections ont une preuve dans les sources, des tests JVM pour certaines fonctions pures et une suite native finale de **61 tests réussis en portrait**. Elle inclut les deux tests ajoutés à `LibraryUiTest` pour l’état sémantique des sections et le focus/activation clavier de la navigation sélectionnée. Les **32 tests UI ont également réussi en paysage puis en portrait à 150 %**, avec captures après correction. Les trois passes sont détaillées dans le [rapport Android](ANDROID_VALIDATION_2026-10-05.md).

La validation utilise exclusivement **Android Emulator, Android SDK, ADB, les tests instrumentés et Logcat**. Les observations et captures viennent de l’émulateur Android API 36.1 ; elles ne sont pas des maquettes ou des rendus de navigateur. Le [rapport Android](ANDROID_VALIDATION_2026-10-05.md) détaille les configurations et les limites des assertions réellement exécutées.

Les contrôles suivants restent hors de la preuve revendiquée ici : ordre et annonces vocales TalkBack, gestes Retour/prédictifs, tablette/multi-fenêtre/charnière, restauration après mort réelle du processus, refus/annulation de tous les fournisseurs SAF externes, réponse biométrique physique, fluidité mesurée, toutes les langues et rendu dans un jeu réel. Une passe texte agrandi ou paysage sur un émulateur ne couvre pas toutes les combinaisons de fenêtre, clavier et appareil. Ces limites ne remettent pas en cause la première exécution native ; elles empêchent d’en faire une validation universelle.
