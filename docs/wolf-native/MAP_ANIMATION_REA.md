# Cartes, animation et audio : preuves W2/W3

Ces contrats proviennent des exécutables officiels utilisés par le corpus local : W2 SHA-256 `795203a6e875618d7fbdc7dd1f409a445c60262c911745553d040081bedb6ac0` et W3 SHA-256 `4ee2a905a5a74a513c885b7096150ffda1a9800180db5b5b0337ad8fd86fbf8e`. Les exports REA sont en lecture seule, dans `build/wolf-rea/wolf2-native-render-followup` et `build/wolf-rea/wolf3-native-followup`. Ils ne remplacent pas une validation du rendu sur Android.

## Ordre des tuiles

Le MPS contient les tuiles dans l'ordre **couche, X, Y**. W2 `00418e20` lit un entier de quatre octets par itération, avec les boucles couche puis X puis Y, et écrit `vector[layer][x][y]`. Son getter `00483260` utilise ce même ordre. Preuve du lecteur : `fmt-map-loader-w2.c.txt`, `ev_9b875627ff99d7082dc4b84f1c32243dd6288063992cecb2db95d9249a0892ec` ; instructions `00419363..004194b2`, `ev_7e850dcac1591dd6bd604cda4deca0b9e86c0fc7fa0b73f7beae6e95051d00a8`.

W3 conserve la même structure native. Le désérialiseur de carte sauvegardée `009f6fe0` copie une colonne entière, `height*4` octets, dans chaque `vector[layer][x]` ; le getter `009f97e0` indexe ensuite Y. Le lecteur MPS appelé par `009f8860` passe par `0065f900` avant d'assigner cette structure. Preuve de structure : `fmt-macro-map-load-actual.c.txt` et `fmt-macro-map-load-wire-asm.asm.txt`, `ev_6e538dbb2c3785c135d3532b6fe9e33202104aebb0d9edd913884b42b192a15a`.

`WolfFormats.parseMap` transpose pendant la lecture vers le contrat portable existant : `tiles[(layer*height+y)*width+x]`. Cela ne demande pas de deuxième copie de la matrice. Les cartes UTF8 `-1` sans tuiles gardent leur tableau vide. Le test `asymmetricWireColumnsBecomeRowsAtEveryLayerAndMapDialect` écrit des octets indépendants pour une carte 2×3, vérifie chaque coordonnée, trois couches pour les versions100..102 et quatre pour103. Les fixtures `WolfMap` écrites directement dans les tests restent row-major.

## Bouclage et registre système

Le MPS ne porte pas ces flags. W2 `0044dcf0` et W3 `009f8860` lisent **SysDB type0, ligne ID de carte, champ3** : 1 boucle X, 2 boucle Y, 3 boucle les deux ; toute autre valeur laisse les deux flags à zéro. W3 stocke X à `map+1e60`, Y à `map+1e61`. Les instructions `009f930b..009f9352` prouvent les arguments du getter `0093e6b0(type,data,field)` : `ev_dfc0d255cbd796761fb2987b335efb6a35b4b3cd4b1c6bacffeb74699888c4e6` et `ev_435b5661be212575a587c8266da4e9ca8a563525bfac1a2872ad1dca4d42c39b`.

`WolfMap.loopX/loopY` sont deux booléens ajoutés en fin de modèle, false par défaut. `WolfParser.loadMap(id)` les renseigne à partir du registre ; `WolfFormats.parseMap` seul ne peut pas les déterminer. Le test `mapLoopingComesFromTheSystemRegistryAndRawMapsStayUnconfigured` construit un jeu complet en mémoire et vérifie 0,1,2,3,4,−1 et Int.MAX_VALUE, ainsi que les valeurs false du parser MPS brut. La suite `WolfFormatsTest` passe **24/24**, avec les fixtures officielles activées via `wolf.fixtureRoot=build/wolf-research`.

L'ordre d'axes interne du helper de recherche de chemin ne se déduit pas du nom des deux champs de carte : voir [les codes spéciaux](SPECIAL_CODES_REA.md). Les adaptations de caméra, collision et répétition graphique doivent utiliser les flags établis et conserver leur propre contrat géométrique.

## Animation des personnages

Le binder W3 `0045e1a0` sur l'objet global `00f511c8` associe `object+120` à `byteSettings[34]`. La lecture du pointeur `00f512e8` dans le tick de personnage est donc le réglage de cycle d'animation **byte34**, pas byte13. Preuves : `fmt-character-config-bind.c.txt`, `ev_b59757d6ac9e98bf4356ea48737a8bb7b8a6ee96aa6948d032c700b1025d6c6b` ; instructions du binder, `ev_301d6ff6d5ea90c1b5b1d81a1f81be2abea2983fa1bf5abb589785be3f5e7cf2`.

Le constructeur W3 `009e6740` écrit movingAnimation=1 et idleAnimation=0 dans les bytes A8/A9. Le reset `009e6d30` initialise le motif de base et le motif de repos à1 pour trois motifs,2 pour cinq. Le constructeur W2 `00444d20` fait movingAnimation=1 en AC, idleAnimation=0 en AD ; `004450b0` initialise les motifs base62/repos4C à1 ou2. Le motif courant W2,4A, est initialisé à1 avant ce reset, y compris pour cinq motifs. Preuves W2 : `ev_b8b830cb905bb77f3dd80f415727d90f20f0fdd69aaa12be6c27632e0de0d0fe`, `ev_f64a02c8f9f164807d80b1f6330d93e9225cac3265f495cbe4f8a8b06f586362`.

Le changement de page W3 `009f41a0` copie `page.graphicFrame` vers le motif courant4E puis vers le motif de repos50. Il n'écrit pas le motif de base66. Le quatrième byte de features, stocké dans `WolfEventPage.pageTransfer`, demande la conservation de direction et motif lorsqu'une page précédente existe. À partir du profil317, le motif conservé est aussi copié vers le repos ; avant317, la branche conserve direction/motif sans réécrire le repos. Preuve : `fmt-character-event-page-apply.c.txt`, `ev_ebf8c96edd0024f0cc3974aee056608fd3a60f8e8d0dbe7160d20ca4679a74c0`.

Les gardes des compteurs de repos restent des bytes distincts de la collision : W2 `00447d80` incrémente idleTicks64 sauf si byte57!=0 et getter `00480e30` retourne zéro ; ce getter lit B0. W3 `009eb000` incrémente idleTicks68 si byte5B==0 ou byteAC!=0. Les deux bytes de chaque paire sont initialisés à zéro. Le sens complet des mutations de ces deux paires n'est pas encore établi ici ; aucun ne doit être renommé « through ». Le through de W2 est53, celui de W3 est57. Preuves W2 : `ev_b3b8a6b82d273c2461f0ce93c3bf452838e1b7e15fe53e2187dffa006eeba2aa`, `ev_72a16f3628d893cdb7bd8738443fb0c9c8877ba8cac8fb451ce656ec44f4c48b`.

## Audio au changement de carte

Le transfert W3 `00a40b10` appelle le loader de carte puis `009f98f0` uniquement lorsque l'ID de carte change. `009f98f0` lit SysDB0/champ1 BGM et champ2 BGS : −3 utilise les chaînes5/6, −2 conserve, −1 arrête, un ID positif charge la ressource. Les helpers reçoivent un fade de5. Sources : `fmt-macro-map-transfer-wrapper.c.txt`, `ev_a314ff084a679029fbe5b08eb391a71c8b250786e9d66feb24c2e079ecdb0365`, et `fmt-macro-audio-map-change-reset.c.txt`, `ev_6bc90a978dc8fd88d72721123e7559d4fe96bbd208eef1c0fb8cc3c1ea79437c`.

W3 diffère sur deux points établis : conserver le BGM avec−2 saute aussi la restauration du volume effectif ; changer le BGS du canal0 arrête d'abord les canaux non nuls avec fade5. Un lecteur à un seul canal BGS ne prouve pas cette dernière sémantique.

La valeur initiale du pitch W2 (Sys96) est100 : le constructeur audio `0047a5a0` l'écrit dans l'objet global. Le volume nominal Sys95, global distinct `00aa6940`, est initialement zéro et reçoit sa valeur à la lecture/changement de carte. Une lecture BSS seule ne permettait pas de conclure à un pitch nul.

W3 a sa propre preuve d'initialisation. Le constructeur statique `004022b0` appelle `009607d0` avec l'objet global `01504820`. `009607d0` écrit pitch BGM100 à+EC, correspondant au getter Sys96 `0150490c` ; il vide la table pitch BGS à+208 puis y insère la clé0 avec100, correspondant au getter Sys98 `01504a28[channel]`. Source `fmt-audio-constructor-w3.c.txt`, `ev_00cbf124575002af442b6e06e4455d2619f63820475d9813223191057c9b0a9e` ; instructions `00960d1e..00960d59`, `ev_8aedd0addd4a20bbc5fac1d717f4dccf59a93cf127697d6ef8c5ba9ab4fa5578`.

Le canal sélectionné est initialement0. Un getter de pitch sur un canal BGS absent utilise `operator[]` et crée une valeur0 ; il ne reçoit pas automatiquement100. Le volume nominal BGM Sys95 (`015056b8`) et la table nominale BGS Sys97 (`015056cc[channel]`) sont distincts du volume effectif100 initialisé par le constructeur audio. Leurs bytes initiaux sont à zéro et leurs références visibles sont les setters, la lecture audio et les changements de carte. Une entrée nominale absente donne0 par le getter ; cette constatation ne prouve pas l'état après lecture d'une ressource audio.

Le réglage de compatibilité de volume nul est établi pour ce binaire W3 : `DAT_00f512fc` est le pointeur de `GameConfig+134`, donc **Game.dat byteSettings[39]**. Le binder `0045e1a0` écrit `bytesBase+27` à cet offset ; son appel initialise ensuite le byte à0 avant lecture de la configuration. Cette liaison utilise les mêmes preuves du binder que le cycle d'animation34 ; elle ne doit pas être extrapolée au binaire W2.

La commande audio `00a18510` applique, dans le mode source fichier, `volume=100` si `volume==0 && byte39==1`. Le pitch nul devient100 indépendamment du réglage. Le lecteur de ressource DB `00962fb0` fait aussi la comparaison stricte `byte39==1` pour les BGM/BGS. Les SE DB ont une branche différente, instructions `009646d5..00964748` : si `DBvol==0 && byte39!=0`, volume effectif=`trunc(100*SEmaster/100)` ; sinon volume effectif=`max(1,trunc(DBvol*SEmaster/100))`. Ce résultat est ensuite multiplié par le facteur Double de l'objet audio à+1D0 et tronqué. Remplacer cette dernière branche par le même helper « byte==1 » perdrait la sémantique native. Preuves : `20-sound-command.c.txt`, `ev_a0e11db56e10e86680cea2b6f43a86768b741221895fbf2d23257383eea39c68` ; `21-audio-play-db.c.txt`, `ev_147081c9526a82c6b02d9e68555a5bd716b26dceb48ac998e79cfffd440a4521` ; exports instructions `fmt-audio-volume-zero-rule-command-asm.asm.txt`, `ev_7242847a2e9e61d7c8bc6b8fd65eb3c2e1795142c66f7dc2126f2e0425da1b8f`, et `fmt-audio-volume-zero-rule-playdb-asm.asm.txt`, `ev_7071a0d93c2aaba64aa49ea0ddbe3a81d5c94e5986adc39c09acdea5cccfa225`.

## Facteur physique des masques W3

Le placement des imports5/6 du masque utilise l'entier `00f4eb60`. Les deux coordonnées logiques sont multipliées par ce facteur (`0097565c/00975663`) avant l'ancrage dans les dimensions physiques du masque. L'image importée n'est pas elle-même redimensionnée par cette routine. La constante `00c8b750` n'est pas ce facteur.

Dans le profil officiel analysé, le PE initialise `f4eb60` à1. Les **253 références directes** données par le `xrefs` public ont été inspectées individuellement avec `inspect_native_instruction` : toutes sont classifiées READ. L'audit reproductible de ces réponses est `fmt-render-mask-factor-reference-audit.json`, référence initiale `ev_297beb85ca6a606da4bf80147ca85b5b4cdee12af5387619698ffdd0cfae8617`, bytes initiaux `ev_7b229716035f4e12b02d1f39d983b1a9da8213028e1edd7867b2da3b94c8ab36`. Aucun setting Game.dat ni écriture directe du facteur n'est établi dans ce binaire. Ce résultat permet le facteur1 pour ce profil ; il ne prouve pas l'absence de mutations indirectes dans tous les profils ou versions du moteur.
