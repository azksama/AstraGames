# Wolf data and archive reader evidence

`WolfArchive` implements a read-only `WolfAssetSource` over positional reads supplied by the host. Opening an archive reads its header and file/directory index; `read(path)` reads and decodes only that asset. It does not extract the archive, recursively scan Android storage, or copy the game directory. Archive ownership transfers to `open`, including failed opens; `close` closes its source. Each source read must return a fresh, exact-length byte array.

## Implemented archive profiles

| Container | Established profile | Key/codec behavior |
| --- | --- | --- |
| DX5 | Wolf 2.01 / 2.10 fixed keys | 32-bit directory/file addresses; historical 12-byte XOR key; optional DX LZ per file |
| DX6 | Wolf 2.20 fixed key | 64-bit addresses; historical 12-byte XOR key; optional DX LZ per file |
| DX8 | crypt version 0, 300, 314 | Established fixed password, CRC-derived 7-byte index/file keys, parent-directory/name key suffixes |
| DX8 | crypt version 331, 350 | Established fixed password, per-archive 15-byte material, address transform, Wolf XOR and modified AES counter streams; positional decoding |
| DX8 | crypt version 1000 | A0 external carrier supplies the Pro 3.1 password; MSVC RNG carrier XOR and CRC-derived index/file keys |
| DX8 | crypt version 1010 | Pro 3.3 carrier supplies its password and four additional key bytes; finite custom RNG/AES carrier transform, archive address/Wolf XOR/modified AES transforms |
| DX8 | crypt version 1020 | Same V2 carrier material selected explicitly for the archive's 1020 header; distinct Pro 3.5 AES key/IV/body seed, address transform and Wolf XOR branches |
| DX8 | crypt version 100 | Established fixed 32-byte ChaCha key and 12-byte nonce, counter one and positional inner streams |
| DX8 | crypt version 200 / CC2 | F1 external carrier's size supplies 64-byte material; 32-byte ChaCha key, 12-byte nonce at offset 34, counter one and positional inner streams |
| DX8 | `NO_KEY`, `NO_HEAD_PRESS` | Clear assets/indices where explicitly declared; raw or Huffman + DX LZ indices |

DX8 supports whole-file and prefix/suffix Huffman compression, optional subsequent DX LZ compression, and the declared CP932 (932), UTF-8 (65001), or ASCII (32765 / 20127) filename code pages. The original name bytes are preserved for key derivation. Paths are decoded before checking separators, including CP932 characters whose second byte is `0x5c`. ASCII filename comparisons ignore ASCII case. Names containing traversal, absolute paths, a colon, a NUL, or decoded separators are rejected. Cycles, repeated directory ownership, duplicate paths, invalid table offsets, truncated reads, and malformed codec lengths are rejected.

Container positions use `Long`, including files beyond 4 GiB. Expanded indices, individual stored assets, and expanded assets remain bounded arrays. Default limits are 64 MiB for an expanded index, 128 MiB for stored input or an expanded asset, 500,000 index entries, 128 directory levels, 4,096 path bytes, and a conservative 256 MiB cumulative index allocation budget. Asset reads are not retained in an archive-wide cache. The host is responsible for limiting concurrent asset decodes and any image/audio caches.

`WolfArchiveKey.fromCarrier(source, expectedCryptVersion, maxCarrierBytes)` derives only the evidenced 1000/1010/1020/200 profiles. It owns and closes the carrier on success or failure. It reads the 31-byte header and at most 255 selected key bytes; it never loads the complete carrier. The default carrier size bound is 256 MiB. A0 requires at least `0x5cb8` bytes, positive key length at offset 19, and the MSVC XOR stream from offset 20. The AES carrier selects bytes using its coprime multiplier and offset-30 AES stream; each selected offset remains checked against the input. The exact 1020 profile must be explicitly supplied by the archive header; future versions are not treated as 1020. A CC2 carrier needs only its header and physical size. `WolfArchive.open(source, carrierKey = key)` verifies that the container and carrier profiles match. Source discovery and scoped file permissions remain responsibilities of the Android host. Wrong keys are not accepted merely because their carrier profile matches: normal index structure, code page, path, and allocation checks still apply.

Both ChaCha profiles mirror the C++ `uint32` cast on the starting inner stream position. The `KeyConvFileRead`/`KeyConvFileWrite` wrappers skip the inner transform when `NO_KEY` (bit 0 of the little-endian flags at offset 44) is declared. Accordingly, 1000/200 need no carrier in that case; 1010/1020 still need it for their outer address/XOR/AES transforms. Profile 100's fixed key and nonce come from `DXArchive.cpp`; it needs no carrier. Unknown DX versions, flag bits, filename code pages, and future Pro/custom protection profiles without a demonstrated external key chain fail with an explicit format error. Recognizing a version is not permission to skip its transform. These readers do not yet implement every Wolf Pro protection variant.

## Implemented metadata envelopes

CommonEvent versions `0x8f` through `0x92` are the ordinary envelopes. Versions `0x93` and `0xcc` share the compressed envelope: a 10-byte signature and version byte, exact compressed/expanded lengths, a raw LZ4 block, and commands with their extension records. Route commands, source offsets, extension bytes, and CP932/UTF-8 strings are preserved. The footer is independent of the version and must be at least `0x89`, followed by exact EOF.

The historical encrypted CP932 Game.dat and CommonEvent.dat headers supply three unsigned one-byte seeds. The body starts at offset 10. The three MSVC RNG XOR passes operate at intervals 1, 2, and 5, using Game.dat seeds at offsets 0/8/6 and CommonEvent.dat seeds at offsets 0/3/9. Decoding uses a new bounded array and does not alter the original data. This historical transform is not applied to database/project/tile files whose envelope has different evidence.

The Pro `P` marker at offset 1 selects a separate envelope even when the first seed is zero. Only the evidenced markers at offset 5 are accepted:

| Marker | Supported metadata | Header/body/key behavior |
| --- | --- | --- |
| `0x54` / T, Pro 3.1 | Game, CommonEvent, Database | Three historical RNG passes; bounded key length at offset 15; UTF-8 body after the key. Database additionally validates the K marker. The first project seed byte is signed. A zero encryption indicator is rejected. |
| `0x55` / U, `0x56` / V, Pro 3.3 | Game, CommonEvent, Database | MT19937 XOR; finite custom RNG-derived AES key/IV; modified AES counter transform over at most 326 bytes; UTF-8 body starts at offset 143. The project seed at decoded offset 20 is unsigned. |
| `0x57` / W, Pro 3.5 | Game, CommonEvent, Database, TileSetData | Signed 32-bit XOR stream; four dynamic salt bytes and the file-specific static salt; Wolf's modified SHA-512 and AES schedule; body starts at offset 143. Database projects use MSVC RNG seed zero, as specified by FileCoder. |

The supported Pro chain uses the empty secret explicitly used by the pinned reference. It does not guess user passwords, external keys, future markers, or undisclosed protection variants. Earlier Pro tileset variants have no demonstrated reader chain and remain rejected. Each database derives its own `.project` key from its paired `.dat`, so decoding another file cannot change global RNG/key state. Cipher transforms provide no authentication; the ordinary readers still check the resulting version, lengths, record structure, encoding, terminators, and EOF. Decryption copies and fixed RNG/hash workspace count against the cumulative allocation budget before allocation.

Game.dat string layouts with 8, 9, 13, or 14 strings are supported. Its size marker must match the physical input size or, for an established protected envelope, the reconstructed clear size. Map dialects 100–103 and database dialects `0xc1`–`0xc4` retain their separate format checks. No protected map chain beyond the evidenced clear/compressed map dialects is inferred. These readers validate data structure; game execution still depends on VM and rendering support for that game's commands and settings.

## Validation and its limits

`WolfArchiveTest` assembles synthetic DX5/DX6/DX8 files independently from the production decoder. It exercises compressed indices and files, whole/partial Huffman, non-ASCII paths, offsets beyond 4 GiB, short reads, malformed trees/tables/tokens, quotas, and source closure. Wolf 331/350 stream and address vectors were generated by compiling the pinned C++ WolfCrypt reference; decoding the same stream in 17-byte positional slices must match decoding it at once.

`WolfArchiveKeyTest` reads three synthetic carriers and ten structured DX8 archives protected with the pinned C++ reference (five profiles with and without the explicit `NO_KEY` flag). For profiles 100/200/1000/1010/1020, all nine plaintext asset SHA-256 digests match the independently assembled fixture; Game/CommonEvent/Database and PNG dimensions parse successfully. The `NO_KEY` fixtures verify that inner decoding is skipped while 1010/1020 outer decoding remains necessary. Carrier reads are recorded and limited to the header plus selected bytes, archive reads to its index and requested assets, and originals remain unchanged. Additional pinned C++ CC2 vectors cover positions 0, 1, 63, 64, 65535, and near `uint32` wrap, sliced reads, and repeated XOR reversal. Missing carriers, zero key lengths, mismatched profiles, a wrong password from an altered carrier, input size limits, and unknown profiles fail and close their source. The local C++ harness is `build/wolf-rea/archive-proof/pro_archive_vectors.cpp`; only its synthetic outputs are tracked under `src/test/resources/archive-pro`.

A separate local-only test reads the official research `runtime/public/Data.wolf` with positional I/O. Its index contains 347 files and expands to 41,772 bytes. Before reading any asset, only the header and stored index are read. The test reads actual CommonEvent/Game/Map/Tileset/SystemDB resources and PNG/OGG bytes, compares known digests, and verifies that the original archive remains unchanged. Proprietary research assets and C++ proof binaries are ignored build inputs, not module or APK assets.

`WolfFormatsTest` uses independent CommonEvent `0xcc` fixtures with routes, extension records, and non-ASCII text; a local official `0x93` fixture is cloned and only its version byte changed for a parser-equivalence check. Original fixtures are preserved.

`WolfMetadataCryptTest` reads 13 raw cipher vectors and three modified SHA-512 vectors generated by compiling the pinned C++ WolfTL routines. The 17 additional structured synthetic fixtures exercise Game.dat's 14 strings/settings, CommonEvent commands/routes/extensions, database/project pairing, and all 31 tileset auto slots/passages. Their plaintext is independently assembled from the wire layout; the C++ reference protects and then decodes each body before emitting a fixture. UTF-8 text, zero first seeds for U/V/W, signed versus unsigned project seeds, caller input preservation, wrong pairings, truncations, unknown profiles, and allocation quotas are checked. Reference harnesses live under the ignored local `build/wolf-rea/archive-proof` research directory; tracked test resources contain only synthetic data.

These proofs establish the listed envelopes, codecs, resource access, and format behavior on the tested corpus. They do not establish complete command compatibility, gameplay, save compatibility, timing, or rendering fidelity for every game. No assets from The Clumsy Witch Seris were supplied for parsing; the user report proves that its CommonEvent version byte is `0xcc`, but does not reveal its protection chain or command corpus.
